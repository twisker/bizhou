# 版本与兼容性

本页说明：各版本改了什么、**旧版本写的数据是否还读得出来**、历史版本去哪里下载，以及为什么这个工具不会自动更新。

---

## 兼容性承诺

加密工具最重要的承诺不是"功能多"，而是**你三年前上传的东西今天还能取回来**。因此：

| 承诺 | 含义 |
|---|---|
| **密文格式向后兼容** | 任何版本的 `bz` 都能解开更早版本上传的 bundle。分片格式、manifest schema、`encMeta` 布局只增字段、不改语义。 |
| **保险库向前兼容** | KDF 参数（scrypt 的 N/r/p）记在**每个保险库文件内部**，解锁时用文件里那份，不用当前版本的默认值。v1.0.x 用 N=2¹⁵ 建的保险库，在 v1.1.0 上照常解锁，不需要迁移、也不会被悄悄改写。 |
| **不可逆动作必须显式** | 会让旧数据解不开的动作（如 `bz init --force` 重铸主密钥）永远需要你手动加参数，绝不会自动发生。 |
| **降级可行** | 装回旧版本仍能读旧数据。但**旧版本不认识新功能**：v1.0.x 不会去云端找保险库，也不认识 `.trash` 回收站里的条目。 |

> 唯一的例外会被明确标注为 **破坏性变更**，并且只可能出现在大版本（major）里。截至目前没有发生过。

## 版本一览

### v1.1.0 —— 云端保险库

**解决的问题：** v1.0.x 的保险库（`vault.json`）只存在本机、从不上云。没有它，主密码和恢复密钥都打不开任何东西——换机、重装、硬盘损坏都会让云端数据**永久锁死**，而文档当时错误地承诺"换机只需重输主密码"。

- **保险库加密上云**：`bz init` 默认把保险库副本放进你自己的网盘，换机只需 `bz login` + `bz unlock`。
- **主密码强度关卡**：上云后云服务商持有该密文、可离线无限次爆破，因此 `bz init` / `bz vault sync` 会**拦下**强度不足的主密码。不愿上云可用 `bz init --no-cloud-vault`。
- **KDF 提参**：scrypt N 从 2¹⁵（32 MiB）提升到 2¹⁷（128 MiB）。老保险库不受影响（见上表）。
- **恢复密钥可重新导出**：`bz vault recovery-key`（须重输主密码）。v1.1.0 之前建的保险库只能 `--rotate` 换新的。
- **百度后端回收站**：`bz trash list/restore/rm/clear` 对百度后端全部可用（建在 `/apps/bizhou/.trash/`）。此前只能到百度网盘 App 里翻。
- **网盘配额**：`bz quota`。

**升级方式：** 用你的包管理器升级（见[安装](./install.html#升级到新版)），然后跑一次 `bz vault sync`。

**升级风险：** 无数据风险。升级不改动任何已上传资源，也不会改写你现有的保险库文件（除非你主动 `vault sync` 或改密码）。

### v1.0.0 —— 首个正式版

客户端加密引擎 + CLI 全部能力：加密上传/还原（字节级一致）、并发上传、断点续传、内容去重、云端真实目录树、递归整树备份、备份守护进程、多类型预览、分享（码 / 7z-AES）、多账号、shell 补全。

**已知问题（v1.1.0 已修）：** 文档六处错误声称"换机只需重输主密码"。实际上必须手工备份密钥根 `~/.bizhou`。若你仍在 v1.0.x，**要么现在备份密钥根，要么升级到 v1.1.0 并 `bz vault sync`**。

## 历史版本

**所有历史版本永久保留**，不做下架：

- **npm**：`npm i -g @bizhou/cli@1.0.0`（任意版本号）。`npm view @bizhou/cli versions` 看全部。
- **GitHub Releases**：[全部 release](https://github.com/twisker/bizhou/releases) 都附带 `bizhou-cli-<版本>.tgz` 与当版 release notes。
- **源码**：每个版本都有对应 git tag（`v1.0.0`、`v1.1.0`……），可自行构建复现。

保留历史版本是开源加密工具的信任基础之一：任何人都能取到某个具体版本的源码与产物，独立验证它们对得上。

> **Homebrew / Scoop 只带最新版**（这是这两个渠道的常规做法）。需要装旧版请走 npm 或 GitHub Release。

## 为什么不自动更新

`bz` **不联网检查版本、不自动升级、不发送任何遥测**。三个理由，按重要性排序：

1. **不发信标**。版本检查是一个周期性的对外请求，会暴露"这台机器在用这个工具"。本项目对定位的要求是低调，不制造这种可观测性。
2. **自动升级一个握着你唯一解密钥匙的工具，风险不对称**。升级失败的代价是"数据打不开"，而晚几天升级的代价通常只是少个新功能。这个选择权应该在你手里。
3. **包管理器已经在做这件事**。`brew outdated`、`scoop status`、`npm outdated -g` 都会告诉你有新版，不需要再造一遍。

真正需要主动触达用户的事情，`bz` 用**本地状态**来判断，而不是查版本号——例如"你的保险库还没上云、换机会锁死"这条，是在 `bz unlock` 时根据本地与云端的实际状态给出的，不联网查任何版本信息。
